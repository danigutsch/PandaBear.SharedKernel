# Library tests

Use the repository-pinned SDK and Microsoft.Testing.Platform runner. After the documented locked restore and Release build, run `dotnet test --solution SharedKernel.slnx -c Release --no-build --no-restore`. Run a single project with `dotnet test --project <path-to-csproj> -c Release --no-build --no-restore`; narrow local debugging with `--filter-class`, `--filter-method`, `--filter-namespace`, or `--filter-trait`. CI selects complete projects and nightly runs cover the full solution.

Provider integration tests require a working local container runtime. Preserve meaningful cancellation, persistence, cleanup, privacy, and boundary regressions. Do not cap test-module concurrency or mask cleanup errors. Analyzer/generator tests exercise compilations and emitted contracts; package consumers validate installed immutable artifacts separately from project-reference tests.

Coverage uses the existing `coverlet.MTP` extension; collection and its limits are documented in the root README. No hosted coverage percentage or service is implied. The two explicitly packaged test-support projects have their own package README files; ordinary test projects remain non-packable.

## Database test assemblies

`SharedKernel.Npgsql.Tests`, `SharedKernel.EventSourcing.Npgsql.Tests` and `SharedKernel.EntityFrameworkCore.Tests` need PostgreSQL. Their fixtures start nothing until a test needs a database, and then borrow a server or start one of their own (see `SharedKernel.Npgsql.Testing/README.md`). The three stay separate assemblies and run in parallel.

- CI runs them together in the `postgres` slice (`sharedkernel-ci run --slice postgres`). The tool starts the owner host `SharedKernel.Npgsql.Testing.Host` once, waits for its ready file, runs the tests with the server connection string in `SHAREDKERNEL_TESTING_POSTGRESQL_CONNECTION_STRING`, and stops the host afterwards, so a complete run creates one PostgreSQL container.
- A plain `dotnet test --solution` or `dotnet test --project` starts no host. Each assembly that runs a test that needs a database starts one server of its own on first demand, so a complete run creates up to one container per assembly, and a run that selects no such test creates none.
- To run assemblies against one server by hand, follow what the tool does: start `dotnet SharedKernel.Npgsql.Testing.Host.dll` from the Release build with standard input from a pipe that you keep open and `SHAREDKERNEL_TESTING_POSTGRESQL_READY_FILE` set to a new file path in a private directory; wait for that file, which holds the connection string as one line; export its content as `SHAREDKERNEL_TESTING_POSTGRESQL_CONNECTION_STRING` for the test run only; then close the pipe, or send SIGTERM, and wait for the host to exit, which removes the container. A second signal ends the host at once, and so does a kill; Aspire's DCP process runs detached and then removes the container within seconds, so that is the way out of a stop that hangs. While Aspire checks for a container runtime the host does not look at stop requests, which takes about a minute when there is none. The host prints neither the connection string nor the password, and exits 1 without a ready file when the server does not start. The borrowed server must be one that Aspire started: `AspireTestApplicationTests` asserts that it listens on a port in DCP's range, so a PostgreSQL on port 5432 fails that test. Aspire hands the generated password to the container runtime as an `-e` argument, so other local users of a shared machine can read it in the process list for about a second while the container is created.
