# Blazor helpers package

Date: 2026-10-27. Status: accepted.

Blazor applications repeat three patterns: mapping a failed HTTP outcome to user copy and showing server validation errors, reporting handled UI failures, and showing accessible upload status. The helpers live in a new package, `PandaBear.SharedKernel.Blazor` (namespace `PandaBear.Blazor`), rather than in `SharedKernel.HttpClients`.

## Why a new package

`SharedKernel.HttpClients` is host-agnostic: it references no UI framework. The helpers need `Microsoft.AspNetCore.Components` (`EditContext`, `ComponentBase`, `ErrorBoundaryBase`), so adding them to HttpClients would force Blazor onto every HTTP client consumer, including services and tools that have no UI.

## Dependencies and cost

- One more package and one more preview surface to maintain, with a public API baseline.
- One new first-party NuGet dependency: `Microsoft.AspNetCore.Components.Web` 10.0.13 (pinned centrally), which brings `Microsoft.AspNetCore.Components`, `.Forms`, `Microsoft.JSInterop`, and `Microsoft.Extensions.*` 10.0.13 packages. The alternative, `FrameworkReference Microsoft.AspNetCore.App`, was rejected: it would limit consumers to projects that use the Web SDK or the shared framework, while the component package works in any Blazor host (Server, WebAssembly, hybrid). The code needs nothing beyond that package. This is flagged as supply-chain surface; it is a Microsoft package from the same release train as the other ASP.NET Core pins.
- A project reference to `SharedKernel.HttpClients`, so consumers receive its existing dependency tree (`Microsoft.Extensions.Http.Resilience`, `Microsoft.Extensions.ServiceDiscovery`, `OpenTelemetry` packages) and, through it, `PandaBear.SharedKernel.Idempotency.Abstractions`. This cannot be avoided because the helpers consume `HttpOutcome` and `UploadOperationState`.
- The components are plain C# classes that build their render tree. The repository has no Razor class library precedent, and the Razor SDK would add a compiler step, static web asset handling, and generated code to the analyzer surface without adding behavior. A component can move to `.razor` later without changing its public API.
- The test project adds the already centrally pinned `bunit` 2.11.3 (the first project to reference it). Test-only transitive packages in `tests/SharedKernel.Blazor.Tests/packages.lock.json`: AngleSharp 1.8.1, AngleSharp.Css 1.1.2, AngleSharp.Diffing 1.1.1, `Microsoft.AspNetCore.Components.WebAssembly` and `.WebAssembly.Authentication` 10.0.10, `Microsoft.JSInterop.WebAssembly` 10.0.10, `Microsoft.ApplicationInsights` 2.23.0, `Microsoft.Bcl.AsyncInterfaces` 6.0.0, `Microsoft.Win32.Registry` 5.0.0, and `System.Security.AccessControl` 6.0.1, plus the resilience, telemetry, Polly 8.4.2, and OpenTelemetry packages that HttpClients already brings, and the xUnit and Microsoft.Testing.Platform packages every test project uses. The old 5.x and 6.0.x packages (`Microsoft.Win32.Registry` 5.0.0, `System.Security.AccessControl` 6.0.1, `Microsoft.Bcl.AsyncInterfaces` 6.0.0) are legacy compatibility packages that arrive through bUnit and Application Insights. They are test-only, no shipped package references them, and vulnerability auditing stays on, so a future advisory fails the build rather than going unnoticed.

## Rules the helpers enforce

- Server-authored validation text is never joined into a free-form message (RFC 9457 leaves `detail` to the server; clients do not parse it). Field-keyed errors go to a `ValidationMessageStore`; everything else shows caller-supplied fixed copy.
- Field names, message lengths, messages per field, and the number of fields are bounded. Text longer than four times the message bound is rejected before any pattern runs, and the stack-trace screening has a match timeout whose expiry counts as unsafe. Blank, multi-line, or stack-trace-like messages are replaced by a caller-supplied field message. Unicode format characters are removed from display text so a file name cannot spoof its extension.
- Server messages clear per field on change and entirely on a new validation request, so a user can resubmit unchanged data.
- Handled UI failures log only the exception type name, an operation name chosen by code, and the trace id, under a stable `EventId`. Handled failures are counted by the reporter itself with the counter `handled_ui_failures_total` on the meter `PandaBear.Blazor`, tagged `error_type` and `operation`; metric creation and increments are fail-safe, so a failing meter factory or listener cannot break the boundary. The counter does not share a series with `unhandled_exceptions_total` in `SharedKernel.AspNetCore`: that counter is request-scoped (`route_template`), and a page failure has no route template, so reusing it would invent data or duplicate the log line. An earlier draft defined an `IHandledFailureCounter` seam that nothing implemented; it was removed before any release.
- Components follow the GOV.UK error summary pattern and standard live-region, progress, and focus semantics. `UploadStatus` keeps its live region to the bounded, throttled announcement; an optional `Detail` fragment renders caller-supplied visible status text in a separate non-live element, so extra detail never floods assistive technology. Optional composite-format strings for the cancel and progress accessible names and progress text, CSS class parameters for the status, progress and cancel elements, and a switch to keep the failure message out of the live region let a consumer keep its own copy and styling; unset, the markup is unchanged, and the component names no CSS framework.

Registry publication, releases, and consumer adoption remain separate actions.
